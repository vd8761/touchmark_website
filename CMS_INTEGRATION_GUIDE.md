### The two API planes

The separation is the most important structural fact about this system.

| | **Admin API** | **Delivery API** |
|---|---|---|
| Base path | `/admin/v1/…` | `/v1/…` |
| Consumer | The admin portal, migration scripts | This website |
| Auth | Session cookie (login) | API key in `Authorization: Bearer` |
| Can do | Everything, all writes | Read published content, write subscribers/forms |

A leaked Delivery key can never reach org settings, billing, members, or another site. Use
Delivery keys for the website. Never put an admin session in the website.

## 3. Decisions taken, and why

Read this section before changing anything — each decision has a reason that is not obvious
from the code.

### 3.1 Article body is `long_text` holding HTML, not `rich_text`

The CMS has a `rich_text` field that stores a structured JSON document. **Do not use it yet.**
Its editor is currently a raw JSON textarea (a known Phase 1 gap), and the Delivery API has
no `?format=html` renderer. Authoring 46 rich articles through a JSON textarea would be
unusable.

`long_text` holding an HTML string is the pragmatic bridge. The site already renders raw HTML
through `HtmlPageRenderer`, so nothing changes on the rendering side. When the block editor
ships, migrate the field then — the entry ids and slugs stay the same.

### 3.2 Website uses a **secret** key, not a publishable one

Next.js fetches content on the server during build and ISR. There is no browser origin to
allowlist, and publishable keys *require* an origin allowlist. A secret key is correct.

It must be `CMS_API_KEY`, **never** `NEXT_PUBLIC_CMS_API_KEY` — the `NEXT_PUBLIC_` prefix
inlines the value into the browser bundle and leaks the key.

### 3.3 Only blog and case studies move to the CMS

The 25 service and industry pages are stable marketing content that changes rarely and has
bespoke layout per page. Moving them into a CMS adds indirection with no editorial benefit.
Leave them as they are.

### 3.4 Cache invalidation is webhook-driven, not time-driven

A 5-minute `revalidate` alone means an author waits 5 minutes to see a correction go live.
The CMS emits a signed `content.published` webhook; the site revalidates on receipt. The time
window stays as a backstop for missed deliveries.

## 5. Phase A — Configure the CMS

Do this once, through the admin portal at <http://localhost:5173>.

### 5.1 Create the site

Sign in as `owner@example.test`. Create an organisation **Touchmark** and a site
**Touchmark Website**. Note the workspace id from the URL or from `GET /admin/v1/auth/me` —
you need it for every Admin API call below. It is referred to as `{WORKSPACE_ID}`.

### 5.2 Content model

Site settings → Content types → Create **Blog Post** (`api_id`: `blog_post`).

> `api_id` is **immutable after creation** — it appears in every Delivery API URL. Get it
> right the first time.

Add these fields. Field `api_id` is derived from the name and is also immutable.

| Name | api_id | Type | Required | Notes |
|---|---|---|---|---|
| Title | `title` | `text` | ✅ | First text field becomes the display title and the slug source |
| Excerpt | `excerpt` | `long_text` | | Cards, meta description fallback |
| Body | `body` | `long_text` | ✅ | The article HTML — see §3.1 |
| Hero Image | `hero_image` | `media` | | |
| Published Date | `published_date` | `date` | | Display date; distinct from `published_at` |
| Author Name | `author_name` | `text` | | |
| Read Time | `read_time` | `text` | | e.g. "6 min read" |
| SEO Title | `seo_title` | `text` | | |
| SEO Description | `seo_description` | `long_text` | | |

> **Adding a `required` field later marks every existing entry incomplete** and blocks
> re-publishing until it is filled. The already-published version stays live. Supply a
> `default_value` when adding a required field to avoid this.

Repeat for **Case Study** (`case_study`) with the same shape if you are migrating those too.

### 5.3 Tags taxonomy

The site already has `/blog/tag` routes. Site settings → Taxonomies → create **Tags**
(`tags`), flat (not hierarchical). Add terms as needed. Exposed at
`GET /v1/taxonomies/tags/terms`.

### 5.4 Create the Delivery API key

Site → **API keys** → Create key:

- **Name:** `Touchmark website production`
- **Type:** `secret`
- **Environment:** `live`
- **Scopes:** `content.read`, `media.read`, `search.read`
- **Allowed IPs:** leave empty (Vercel build IPs are not stable)
- **Rate limit:** leave default (1,000/min for secret keys)

The plaintext `sk_live_…` is shown **exactly once**. Copy it now — it is stored only as a
SHA-256 hash and cannot be recovered. If lost, use **Rotate** (which issues a replacement and
keeps the old key working through a grace window) rather than Revoke.

Create a second key with environment `test` for local development.

### 5.5 Create the revalidation webhook

Site → **Webhooks** → Add endpoint:

- **Name:** `Next.js revalidation`
- **URL:** `https://touchmarkdes.com/api/revalidate` (or your ngrok URL for local testing)
- **Events:** `content.published`, `content.unpublished`, `content.updated`

Copy the `whsec_…` signing secret — also shown once.

Use **Send test** on the endpoint and check the delivery log. Each delivery expands to show
the exact payload sent, the response body received, the attempt number and the next retry
time. Failed deliveries retry at 1m/5m/15m/1h/6h/12h/24h, then dead-letter; 15 consecutive
failures auto-disable the endpoint.

### 6.2 `services/cms.ts` — the delivery client

All CMS access goes through this module. `preventDirectAPICalls` forbids `fetch` in pages and
components.

```ts
/**
 * Delivery API client.
 *
 * Server-side only — CMS_API_KEY is a secret key and must never reach the browser.
 * Every response is wrapped in a { data, meta } envelope which is unwrapped here so
 * callers never see it.
 */

const CMS_URL = process.env.CMS_API_URL;
const CMS_KEY = process.env.CMS_API_KEY;

/** Cache tag revalidated by the CMS webhook — see app/api/revalidate/route.ts. */
export const CMS_CACHE_TAG = 'cms';

/** Backstop for a webhook that never arrives. The webhook is the fast path. */
const DEFAULT_REVALIDATE_SECONDS = 300;

export interface CmsEntry<TData> {
  id: string;
  type: string;
  slug: string | null;
  locale: string;
  status: 'draft' | 'in_review' | 'scheduled' | 'published' | 'archived';
  data: TData;
  seo: Record<string, unknown> | null;
  published_at: string | null;
  updated_at: string;
}

export interface BlogPostData {
  title: string;
  excerpt?: string;
  body?: string;
  hero_image?: string;
  published_date?: string;
  author_name?: string;
  read_time?: string;
  seo_title?: string;
  seo_description?: string;
}

export type BlogPost = CmsEntry<BlogPostData>;

interface ListResponse<T> {
  data: T[];
  meta: { total: number; limit: number; has_more: boolean; next_cursor: string | null };
}

async function delivery<T>(path: string, revalidate = DEFAULT_REVALIDATE_SECONDS): Promise<T> {
  if (!CMS_URL || !CMS_KEY) {
    throw new Error('CMS_API_URL and CMS_API_KEY must be set.');
  }

  const response = await fetch(`${CMS_URL}${path}`, {
    headers: { Authorization: `Bearer ${CMS_KEY}` },
    next: { revalidate, tags: [CMS_CACHE_TAG] },
  });

  if (!response.ok) {
    // The CMS names the failing condition in every error — surface it rather than
    // a bare status code, because "insufficient_scope" and "key_revoked" have very
    // different fixes.
    const detail = await response.text().catch(() => '');
    throw new Error(`CMS ${response.status} on ${path}: ${detail.slice(0, 300)}`);
  }

  return response.json() as Promise<T>;
}

/** Published posts, newest first. */
export async function listBlogPosts(limit = 100): Promise<BlogPost[]> {
  const body = await delivery<ListResponse<BlogPost>>(
    `/v1/content/blog_post?limit=${limit}&sort=-published_at`,
  );
  return body.data;
}

/** One post by slug, or null when it does not exist or is unpublished. */
export async function getBlogPost(slug: string): Promise<BlogPost | null> {
  try {
    const body = await delivery<{ data: BlogPost }>(
      `/v1/content/blog_post/${encodeURIComponent(slug)}`,
    );
    return body.data;
  } catch {
    return null;
  }
}

/** Ranked full-text search across published content. */
export async function searchContent(query: string, limit = 20) {
  const body = await delivery<ListResponse<{ kind: string; data: BlogPost }>>(
    `/v1/search?q=${encodeURIComponent(query)}&type=content&limit=${limit}`,
    60,
  );
  return body.data;
}

/** Terms of the `tags` taxonomy. */
export async function listTags() {
  const body = await delivery<ListResponse<{ id: string; name: string; slug: string }>>(
    '/v1/taxonomies/tags/terms',
  );
  return body.data;
}
```

### 6.3 Delivery API reference for this integration

Full detail at <http://localhost:4000/docs>. What you need:

| Endpoint | Purpose |
|---|---|
| `GET /v1/content/blog_post` | List. Params: `limit` (max 100), `cursor`, `sort` (`-published_at,title`), `locale`, `fields`, `filter[…]` |
| `GET /v1/content/blog_post/{slug}` | One entry by slug |
| `GET /v1/content/id/{id}` | One entry by id |
| `GET /v1/content/blog_post/{slug}/related` | Related entries |
| `GET /v1/search?q=&type=content` | Ranked full-text search |
| `GET /v1/media` / `GET /v1/media/{id}` | Media assets |
| `GET /v1/taxonomies` / `/v1/taxonomies/{apiId}/terms` | Taxonomies |
| `GET /v1/menus/{apiId}` | Resolved menu; entry links resolve to the entry's **current** slug |
| `GET /v1/me` | Echoes the key's workspace, scopes and limits — use to debug auth |

Only `published` entries are returned. Responses carry `Cache-Control: public, max-age=60,
stale-while-revalidate=300` and an `ETag`.

Rate limit headers on every response: `X-RateLimit-Limit`, `X-RateLimit-Remaining`,
`X-RateLimit-Reset`.

### 6.4 Article route — replaces 46 files with one

Delete every `app/blog/articles/<slug>/page.tsx` **after** Phase C has imported them, then
create `app/blog/articles/[slug]/page.tsx`:

```tsx
import { notFound } from 'next/navigation';
import type { Metadata } from 'next';

import { getBlogPost, listBlogPosts } from '@/services/cms';

export const revalidate = 300;
export const dynamicParams = true;

export async function generateStaticParams() {
  const posts = await listBlogPosts();
  return posts
    .filter((post) => post.slug)
    .map((post) => ({ slug: post.slug as string }));
}

export async function generateMetadata(
  { params }: { params: Promise<{ slug: string }> },
): Promise<Metadata> {
  const post = await getBlogPost((await params).slug);
  if (!post) return {};

  return {
    title: post.data.seo_title ?? post.data.title,
    description: post.data.seo_description ?? post.data.excerpt,
    openGraph: {
      title: post.data.seo_title ?? post.data.title,
      description: post.data.seo_description ?? post.data.excerpt,
      images: post.data.hero_image ? [post.data.hero_image] : undefined,
      type: 'article',
      publishedTime: post.published_at ?? undefined,
    },
  };
}

export default async function Page({ params }: { params: Promise<{ slug: string }> }) {
  const post = await getBlogPost((await params).slug);
  if (!post) notFound();

  return (
    <article className="overflow-x-hidden lg:overflow-x-auto">
      <h1>{post.data.title}</h1>
      {post.data.author_name && <p>{post.data.author_name}</p>}
      {post.data.published_date && (
        <time dateTime={post.data.published_date}>
          {new Date(post.data.published_date).toLocaleDateString()}
        </time>
      )}
      {/* Body is trusted HTML authored in the CMS by an authenticated editor.
          Do not render untrusted input through this path. */}
      <div dangerouslySetInnerHTML={{ __html: post.data.body ?? '' }} />
    </article>
  );
}
```

`dynamicParams = true` means a post published after the last build renders on first request
rather than 404ing.

### 6.6 Revalidation route

`app/api/revalidate/route.ts`:

```ts
import { createHmac, timingSafeEqual } from 'node:crypto';
import { revalidateTag } from 'next/cache';
import { NextResponse } from 'next/server';

import { CMS_CACHE_TAG } from '@/services/cms';

export const runtime = 'nodejs';

/** The CMS signs with a 5-minute tolerance; reject anything older. */
const TOLERANCE_SECONDS = 300;

export async function POST(request: Request) {
  const secret = process.env.CMS_WEBHOOK_SECRET;
  if (!secret) {
    return NextResponse.json({ error: 'not configured' }, { status: 500 });
  }

  // The raw body is what was signed — parsing and re-serialising would change
  // the bytes and break verification.
  const raw = await request.text();
  const header = request.headers.get('x-signature') ?? '';

  const timestamp = header.match(/t=(\d+)/)?.[1];
  const signature = header.match(/v1=([a-f0-9]+)/)?.[1];
  if (!timestamp || !signature) {
    return NextResponse.json({ error: 'unsigned' }, { status: 401 });
  }

  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > TOLERANCE_SECONDS) {
    return NextResponse.json({ error: 'stale' }, { status: 401 });
  }

  const expected = createHmac('sha256', secret).update(`${timestamp}.${raw}`).digest('hex');
  const expectedBuffer = Buffer.from(expected);
  const actualBuffer = Buffer.from(signature);

  if (
    expectedBuffer.length !== actualBuffer.length ||
    !timingSafeEqual(expectedBuffer, actualBuffer)
  ) {
    return NextResponse.json({ error: 'bad signature' }, { status: 401 });
  }

  revalidateTag(CMS_CACHE_TAG);
  return NextResponse.json({ revalidated: true });
}
```

**Delivery is at-least-once.** The CMS retries on any non-2xx, so the same event can arrive
twice. `revalidateTag` is idempotent, so this route is safe. If you later do something with
side effects here, deduplicate on the `X-Event-Id` header.

To test locally, expose the site with ngrok and point the webhook URL at it.

## 7. Phase C — Migrate the 46 existing articles

One-off script, run from the website repo. It reads each existing `page.tsx`, extracts title
and body with `cheerio` (already a dependency), and creates + publishes an entry.

### 7.1 Admin API calls the script needs

Authenticate once by login; the session cookie carries the rest.

```
POST   /admin/v1/auth/login                                     { email, password }
POST   /admin/v1/workspaces/{ws}/content/{typeId}               { slug?, locale?, data, seo? }
PATCH  /admin/v1/workspaces/{ws}/content/entries/{entryId}      { data, seo?, change_note? }
POST   /admin/v1/workspaces/{ws}/content/entries/{entryId}/publish
```

- `{typeId}` accepts the content type **id or api_id** — `blog_post` works.
- `data` is keyed by field `api_id`.
- Entry creation uses **relaxed validation** — required fields may be empty, so a
  half-finished import is never rejected outright. Publishing applies the strict pass.
- `PATCH` **merges** into existing values; omitted fields are left untouched.

### 7.2 `scripts/migrate-articles.mjs`

```js
/**
 * One-off import of the hardcoded blog articles into the CMS.
 *
 * Idempotent: re-running skips slugs that already exist, so a partial run can be
 * resumed without creating duplicates.
 *
 * Usage:
 *   node scripts/migrate-articles.mjs           # dry run, prints what it would do
 *   node scripts/migrate-articles.mjs --commit  # actually writes
 */
import { readFile, readdir } from 'node:fs/promises';
import { join } from 'node:path';
import * as cheerio from 'cheerio';

const CMS_URL = process.env.CMS_API_URL ?? 'http://localhost:4000';
const WORKSPACE_ID = process.env.CMS_WORKSPACE_ID;
const EMAIL = process.env.CMS_EMAIL ?? 'owner@example.test';
const PASSWORD = process.env.CMS_PASSWORD ?? 'development-password-1';
const ARTICLES_DIR = 'app/blog/articles';
const COMMIT = process.argv.includes('--commit');

async function login() {
  const response = await fetch(`${CMS_URL}/admin/v1/auth/login`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ email: EMAIL, password: PASSWORD }),
  });
  if (!response.ok) throw new Error(`Login failed: ${response.status}`);
  return response.headers.getSetCookie().join('; ');
}

async function admin(cookie, path, init = {}) {
  const response = await fetch(`${CMS_URL}${path}`, {
    ...init,
    headers: { 'Content-Type': 'application/json', Cookie: cookie, ...(init.headers ?? {}) },
  });
  if (!response.ok) {
    throw new Error(`${init.method ?? 'GET'} ${path} → ${response.status} ${await response.text()}`);
  }
  return response.status === 204 ? null : response.json();
}

/** Pulls the title and the article markup out of one generated page.tsx. */
function extract(source) {
  const title = source.match(/<title>([\s\S]*?)<\/title>/)?.[1]?.trim() ?? null;
  const description = source.match(/<meta name="description" content="([\s\S]*?)"/)?.[1] ?? '';

  const $ = cheerio.load(source);
  // Adjust this selector after inspecting a few files — the generated pages are not
  // guaranteed to be uniform, and a wrong selector silently imports empty bodies.
  const body =
    $('article').html() ??
    $('.blog-details, .blog-content, main').first().html() ??
    null;

  return { title, description, body };
}

async function main() {
  if (!WORKSPACE_ID) throw new Error('Set CMS_WORKSPACE_ID.');

  const cookie = await login();
  const existing = await admin(cookie, `/admin/v1/workspaces/${WORKSPACE_ID}/content/blog_post?limit=100`);
  const taken = new Set(existing.data.map((entry) => entry.slug));

  const slugs = await readdir(ARTICLES_DIR);
  let created = 0;
  let skipped = 0;

  for (const slug of slugs) {
    if (taken.has(slug)) {
      skipped += 1;
      continue;
    }

    const source = await readFile(join(ARTICLES_DIR, slug, 'page.tsx'), 'utf8');
    const { title, description, body } = extract(source);

    if (!title || !body) {
      console.warn(`SKIP ${slug} — title=${Boolean(title)} body=${Boolean(body)}`);
      continue;
    }

    if (!COMMIT) {
      console.log(`WOULD CREATE ${slug} — "${title}" (${body.length} chars)`);
      created += 1;
      continue;
    }

    const entry = await admin(cookie, `/admin/v1/workspaces/${WORKSPACE_ID}/content/blog_post`, {
      method: 'POST',
      body: JSON.stringify({
        slug,
        data: { title, excerpt: description, body, seo_description: description },
      }),
    });

    await admin(
      cookie,
      `/admin/v1/workspaces/${WORKSPACE_ID}/content/entries/${entry.data.id}/publish`,
      { method: 'POST', body: JSON.stringify({}) },
    );

    console.log(`CREATED ${slug}`);
    created += 1;
  }

  console.log(`\n${COMMIT ? 'Created' : 'Would create'} ${created}, skipped ${skipped}.`);
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
```

### 7.3 Migration procedure

1. **Inspect three or four article files by hand** and confirm the `extract()` selector picks
   up the right element. The pages were machine-converted and may not be uniform. A wrong
   selector imports 46 empty bodies.
2. Dry run: `node scripts/migrate-articles.mjs`
3. Spot-check the output — title present, body length plausible.
4. Commit: `node scripts/migrate-articles.mjs --commit`
5. Compare a few articles in the admin portal against the live pages.
6. **Only then** delete `app/blog/articles/<slug>/page.tsx` and add the `[slug]` route.
7. Keep the deletion as its own commit so it can be reverted independently.

### 7.4 Images

Article HTML references absolute URLs on `touchmarkwf.com`. Two options:

- **Leave them.** Fastest, but keeps a dependency on the legacy host staying up.
- **Upload to the CMS.** Three steps: `POST /media/upload-url` → `PUT` the bytes to the
  returned URL → `POST /media/{assetId}/complete`. Then rewrite the `src` attributes. The
  CMS verifies real size, magic-byte type and dimensions on completion.

Prefer WebP (`enforceWebPImages`). Note the CMS does **not** yet generate responsive
variants or blurhash — originals are served at full size.

## 11. Production deployment

**Vercel cannot host the CMS API.** NestJS with a polling job worker needs a long-lived
process; serverless functions do not provide one.

| Component | Host | Why |
|---|---|---|
| PostgreSQL | **Neon** | Serverless Postgres, branching |
| CMS API + admin portal | **Render** Web Service | Long-lived process for the job worker |
| Touchmark website | **Vercel** | Next.js native |
| Media | **Cloudflare R2** or S3 | Render's disk is ephemeral |

### 11.1 Neon

Create the project. Then, in the SQL editor, create the application role **before** running
the RLS bootstrap — `rls.sql` creates the role with a hardcoded development password if it
does not already exist, which you must not ship:

```sql
CREATE ROLE cms_app LOGIN PASSWORD 'generate-a-long-random-password' NOBYPASSRLS;
```

Take two connection strings:

| Env var | Which endpoint | Suffix |
|---|---|---|
| `DATABASE_URL` | **Pooled** (`…-pooler.neon.tech`), as `cms_app` | `?pgbouncer=true&connection_limit=1` |
| `DATABASE_ADMIN_URL` | **Direct**, as the owner role | none |

`?pgbouncer=true` is not optional — Prisma's prepared statements break under transaction
pooling without it.

Then verify the safety property actually holds:

```sql
SELECT rolname, rolbypassrls FROM pg_roles WHERE rolname = 'cms_app';
```

`rolbypassrls` **must** be `f`.

> **This is the most dangerous misconfiguration in the entire system.** Row-level security is
> the last line of tenant isolation. If `DATABASE_URL` points at the owner role, or at any
> role with `BYPASSRLS`, every policy silently stops applying — no error, no warning, and
> cross-tenant reads become possible. Check this after every infrastructure change.
>
> Neon may not permit `ALTER ROLE … NOBYPASSRLS` from the bootstrap script, which is why the
> role is created explicitly above. Re-run the query to confirm.

### 11.2 Render — Web Service

Root directory: repository root (it is an npm workspaces monorepo).

**Build command**

```bash
npm ci && npm run build --workspace @cms/shared && npm run build --workspace @cms/api
```

**Pre-deploy command**

```bash
npm run db:deploy --workspace @cms/api && npm run db:rls --workspace @cms/api
```

`db:deploy` runs `prisma migrate deploy` (never `migrate dev` in production). `db:rls` applies
the policies and grants, and is idempotent.

**Start command**

```bash

```

**Environment**

```bash
NODE_ENV=production
PORT=4000
APP_URL=https://cms.touchmarkdes.com
API_URL=https://cms.touchmarkdes.com

DATABASE_URL=<neon pooled, cms_app, ?pgbouncer=true&connection_limit=1>

JWT_SECRET=<openssl rand -base64 48>
ENCRYPTION_KEYS=v1:<node -e "console.log(require('crypto').randomBytes(32).toString('base64'))">
COOKIE_SECURE=true
COOKIE_DOMAIN=cms.touchmarkdes.com
```

`ENCRYPTION_KEYS` is **required** in production — development falls back to a key derived
from `JWT_SECRET`, production does not. Format is `keyId:base64key`, newest first; keep old
keys listed so values encrypted under them still decrypt.

**Do not use the free tier.** It spins down when idle, which stops the job worker — scheduled
publishing and webhook delivery halt until the next request wakes the service. Starter tier
minimum.

**Media must be S3/R2.** Render's filesystem is ephemeral; the local driver loses every
upload on redeploy.

### 11.3 The admin portal — read this before deploying

Session cookies are `SameSite=Lax`, which browsers **do not send on cross-site requests**.
Hosting the admin SPA on a different origin from the API means login appears to succeed and
every subsequent request returns 401.

Pick one:

**Option A — serve the SPA from the API (recommended).** Single origin, nothing to configure.
Requires a small change to `apps/api/src/main.ts` to serve `apps/admin/dist` statically with
an SPA fallback, and adding the admin build to Render's build command.

**Option B — host on Vercel behind rewrites.** Keeps the browser on one origin:

```json
{
  "rewrites": [
    { "source": "/admin/:path*", "destination": "https://cms-api.onrender.com/admin/:path*" },
    { "source": "/v1/:path*", "destination": "https://cms-api.onrender.com/v1/:path*" }
  ]
}
```

Do **not** "solve" this by switching cookies to `SameSite=None` without understanding the
CSRF implications.

### 11.4 Vercel — the website

no `NEXT_PUBLIC_` prefix.

Update the CMS webhook URL to the production domain once deployed.

**Do this immediately after deploy, before the URL is shared.** After that, registration and

## 12. Gotchas that will bite you

| Symptom | Cause |
|---|---|
| Admin login succeeds, then everything 401s | Admin and API on different origins. `SameSite=Lax`. See §11.3 |
| Cross-tenant data visible | `DATABASE_URL` points at an owner or `BYPASSRLS` role. §11.1 |
| Prisma errors under load on Neon | Missing `?pgbouncer=true` |
| Uploads vanish after redeploy | `S3_BUCKET` unset — using the ephemeral local driver |
| Scheduled publishing stops overnight | Render free tier spun the service down |
| Cannot decrypt email provider credentials after redeploy | `ENCRYPTION_KEYS` changed or unset |
| `422` creating an API key | Publishable key requested a server-only scope, or has no origin allowlist |
| Cannot register a new user | Working as designed — an admin must create the account |
| Webhook 401s at your site | Body was parsed before verification; the raw bytes are what is signed |
| New article 404s | Published? `dynamicParams` true? Webhook delivered? |
| Article body imports empty | `extract()` selector does not match the generated markup. §7.3 |

## 13. CMS limitations to design around

Honest list. None block this integration; all affect what you should promise.

| Limitation | Impact | Workaround |
|---|---|---|
| Rich text is edited as raw JSON | Unusable for authoring articles | Use `long_text` with HTML (§3.1) |
| No `?format=html` rendering | Delivery returns stored values verbatim | Store HTML directly |
| No responsive image variants or blurhash | Full-size originals served to all viewports | Upload pre-sized WebP |
| Search GIN index unused under RLS | Search filters within a workspace rather than using the index | Fine at this scale; documented in the CMS's `docs/PROJECT_STATUS.md` §11.4 |
| Media search is `ILIKE`, not full-text | Filename/alt/caption substring only | Acceptable |
| No SDK, no hosted docs, no playground | Hand-written client (§6.2) | This guide |
| Audience/email/automations not built | No subscriber management, campaigns or automations | Keep the existing Resend contact route (§8) |
| Admin/auth rate limiting is in-process | N instances allow N× the limit | Run one API instance, or accept it |
| No image CDN purge on publish | Media URLs are immutable, so this rarely matters | — |
| Portal has no browser test coverage | UI regressions are caught by hand | Verify visually after CMS upgrades |

The authoritative, continuously updated status is
`C:\Projects\cms\docs\PROJECT_STATUS.md`. Read it before planning further work.
